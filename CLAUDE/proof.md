# 證明策略

方法論、技術、除錯。

---

## 方法論

- **結構優先**：優先使用結構性論證（universal property、自然性、函子性等），而非計算性或逐元素的方法
- **正確的抽象層次**：在最自然的層次上工作——不過度抽象，也不過度具體
- **對偶意識**：對偶版本應從原版機械地對稱推導
- **簡潔即深刻**：冗長的證明往往意味著缺少正確的觀點

### 攻克困難證明

面對困難證明時，依序考慮以下策略：

1. **尋找正確的抽象**：問題是否可以提升到更一般的層次？是否是某個已知性質的特例？
2. **分解為已知結構**：能否將問題拆解為「已有 API」的組合？
3. **改變觀點**：是否可以從不同的表示或等價形式切入？（如：用 Hom 集合重新表述、用伴隨轉置、用等價範疇）
4. **引入輔助構造**：若直接證明困難，考慮構造中間的 isomorphism 或態射作為橋梁
5. **退化到元素**：只有在結構性方法都不奏效時，才退化到 element-wise 或 pointwise 的證明

### 簡化證明

1. **消除不必要的展開**：若 `simp` 可以處理，不要手動 `rw`
2. **辨識隱藏的結構**：手動的 rewrite 鏈，往往可以被一個 `simp` 或更高層的引理取代
3. **提取模式**：若同一個論證模式出現多次，它應該成為一個 lemma
4. **利用對偶**：對偶版本的證明不應獨立撰寫，而應盡可能從原版機械推導

---

## 技術

- 優先使用 term-mode 證明（如 `congrArg`、`congrFun`、`funext`）
- 簡單的等式證明用 `by simp` 或 `by grind`
- 結合律等代數性質用 `by grind` 或 `by simp [←Category.assoc]`
- 避免冗長的 tactic chain——若超過 5 行，考慮提取輔助 lemma
- `aesop_cat` 僅用於 structure 欄位的預設證明
- **禁止**將多行壓縮成一行當成簡化

---

## 除錯

1. 用 `fail "stop"` 查看精確的 goal state，不要盲目嘗試 tactic
2. 檢查型別對齊——universe level、implicit 參數、coercion
3. 檢查 `simp` lemma 是否遺漏 `@[simp]` 屬性
4. 考慮是否需要先 unfold 定義
